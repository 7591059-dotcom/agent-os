# Архитектура 2.0

Полное актуальное описание: [SYSTEM-DESIGN_RU.md](SYSTEM-DESIGN_RU.md).

Обновление 2.0.1: [результаты проверки](REVIEW_2026-09-26_RU.md). Общая блокировка в `process_lock.py` используется приложением и offline-обслуживанием на Windows/Linux. План, новые агенты и включение в проект записываются атомарно. `request_started` отличает ожидающий слот от потенциально оплаченного запроса. Контекст проекта передаётся исполнителю как справочное сообщение, без конфигурации интеграций. `reports.py` формирует приватный отчёт задачи; пользовательские тексты сохраняются внутри буквальных Markdown-блоков.

Это приложение для одного владельца: FastAPI, SQLite WAL, один процесс и русская веб-панель. Twenty подключается как отдельная CRM по API. PostgreSQL и Redis его Compose-профиля не используются агентным ядром. Совместной системы входа пока нет.

| Компонент | Ответственность |
| --- | --- |
| `main.py`, `security.py`, `db.py` | Вход, CSRF/Origin/Host, TOTP, шифрование, атомарные записи |
| `workspace.py` | Проекты, навыки, маски, чаты, расписания, CRM, рекомендации JEV |
| `engine.py`, `workflow.py` | Приём идеи, ревизии, согласование, DAG, бюджеты и восстановление |
| `agent_runtime.py` | Настроенные инструкции и навыки, диалог модели, предложения инструментов |
| `toolbus.py` | MCP-каталог, grants, точные аргументы, согласования и исполнение |
| `jev.py` | Официальный API TypeSafe, только рекомендация |
| `providers.py`, `net.py` | Модельные API и ограниченный исходящий HTTPS |
| `telegram.py` | Несколько ботов, изоляция пользователей, идеи/чаты/согласования |
| `publications.py`, `integrations.py` | Черновик, отдельное одобрение и отправка публикации |
| `static/` | Русский интерфейс без внешних CDN |
| `services/maintenance/` | Отдельный MCP для чтения кода и сохранения предложений изменений |
| `deployment/` | Дополнительные Compose-профили и инструкции |

Задача проходит `backlog → planning → ready → running → done`; ошибки дают `failed`, предусмотрены пауза и отмена. Идея с согласованием начинается с `review`. Ручной план сразу получает `ready`. Независимые шаги выполняются параллельно в пределах общего семафора движка.

Запрос MCP проходит `pending → checking → executing → done`. Отказ, изменение прав, тайм-аут и неопределённый внешний результат сохраняются отдельно. Отказ возможен и во время `checking`; перед `executing` проверяются права, исходный запрос и весь актуальный каталог. После неопределённой отправки автоматического повтора нет. Каждый вызов требует нового согласования; JEV его не заменяет.

Браузерные `POST /api/publications/{id}/approve` и `/publish` требуют заголовок `X-Resource-Version` со значением `updated_at` показанной записи. Проверка версии и смена статуса происходят атомарно. Отсутствующая или устаревшая версия даёт 400. После одобрения отправка использует новую версию из ответа. `GET /api/tasks/{id}/export` требует сессию владельца и возвращает Markdown-вложение с `Cache-Control: no-store`.

При обычном перезапуске незавершённые чаты и согласования не возобновляют инструменты сами. При восстановлении резервной копии дополнительно отключаются боты, расписания, MCP/JEV/CRM, отзываются сессии, старые кнопки и предпросмотры. Неизвестное потребление токенов сохраняет отметку неопределённости.

Действующие ограничения: один владелец, SQLite, отсутствие глобального денежного лимита, прямого shell и автоматического применения кода. Указанные в проекте токены ограничивают выполнение, но не гарантируют верхнюю границу счёта провайдера.
