Состав: 122 прежние серверные проверки и 39 новых регрессий в `test_engine_regressions.py`, `test_security_regressions.py`, `test_project_regressions.py`, `test_local_regressions.py`. Изменения и дальнейшие приоритеты: [отчёт](REVIEW_2026-09-26_RU.md).

DOM-сценарий дополнительно проверяет запоздалые ответы, переключение окон, сохранность следующего сообщения, повторный submit, версию публикации, отчёт, отказ MCP в checking и отметку неопределённого расхода чата. Windows runner завершает тестовый сервер через собственный stdin-канал без рабочего HTTP-endpoint выключения.

Границы текущей проверки:

- Node **24.13.1**, jsdom **30.0.1**. DOM-сценарий прошёл, но npm предупреждает: jsdom объявляет поддержку `^22.22.2 || ^24.15.0 || >=26.0.0`. Для воспроизводимого CI используйте подходящую версию Node. Системный Node не заменялся.
- Браузерный размер примерно **1280×720**. Это целевой проход, не полная проверка мобильной раскладки и всех браузеров.
- Docker CLI установлен, движок недоступен. Образы, Compose, Caddy, Twenty, TLS, volumes и VPS этим обновлением не проверены. Образ остаётся на Python 3.12.
- Внешние Telegram/LLM/JEV/MCP/CRM требуют проверки на своих аккаунтах с ограниченными правами. Имитация не подтверждает фактическую совместимость, качество и стоимость.
- Windows Python: проверены приложение и обслуживание отдельными процессами. Приватность `.env` определяется NTFS ACL, а не POSIX mode bits. См. [LOCAL-WINDOWS.md](../LOCAL-WINDOWS.md).
- Полный пентест, аудит всех транзитивных зависимостей и длительная нагрузка не выполнялись.

Новые сценарии охватывают проекты/навыки/маски, ручной и автоматический план, чат и расписание, сокрытие секретов, разрешения MCP, изменение каталога, конкурирующее подтверждение, неопределённый внешний результат без автоповтора, ожидание согласования агентом, официальный формат JEV, защиту исходников maintenance MCP и привязку Telegram-предпросмотра к боту/пользователю.

Новые формы отправляют запросы настоящему временному серверу. Старые Telegram fixtures дополнены серверными тестами. Чат использует явно демонстрационный провайдер.

## Что это не подтверждает

- **Настоящий браузер:** визуальная проверка не выполнена; загрузка браузера Playwright в этой среде не удалась. JSDOM не проверяет раскладку, мобильный экран и реальный фокус.
- **Docker/Compose:** Docker отсутствует. Разбор YAML не заменяет `docker compose config`, сборку образов, работу Caddy, миграции Twenty и проверку прав volumes. Исправлено включение maintenance-файлов в Docker build context, но сборка не запускалась.
- **Реальные API:** JEV, MCP, Telegram, Twenty и социальные адаптеры проверялись на подменённых ответах. Действительные permissions, ключи, расходы и результат во внешнем аккаунте требуют отдельной приёмки.
- **VPS и Windows:** установку на сервер пользователя и выполнение Windows `.cmd` не проводили. DNS/TLS, firewall, восстановление полного стека, обновление существующей базы и нагрузка проверяются на целевой установке.
- **Безопасность:** пентест и полный аудит зависимостей не выполнены. Меры и остаточные риски описаны в SECURITY-REVIEW.md и SYSTEM-DESIGN_RU.md.

## Первый приёмочный сценарий

1. Запустить копию в demo-режиме, проверить вход, проект, ручной план, чат и сохранение после перезапуска.
2. На HTTPS включить TOTP и подключить одного провайдера; выполнить небольшую задачу с реальным ответом.
3. Подключить одного бота, проверить свой и чужой user ID, затем MCP с безопасным чтением. Убедиться, что без согласования вызова нет.
4. Для Twenty: завершить защищённую первоначальную настройку, закрыть регистрацию, выдать ограниченный ключ, импортировать запись дважды и получить одну задачу.
5. Проверить резервирование и восстановление на отдельной копии. Только после этого включать нужные расписания и рабочие интеграции.
