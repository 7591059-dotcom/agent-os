# Развёртывание и обслуживание Агентной

Версия 2.0: этот файл описывает ядро ОС. Для отдельной CRM добавьте [профиль Twenty](../deployment/twenty/README_RU.md), для предложений изменений кода — [maintenance MCP](../deployment/maintenance/README_RU.md). Вместе они требуют больше памяти; 2 ГБ ниже относятся только к ядру. Docker-запуск текущей сборки в среде разработки не проверялся.

## 1. Что подготовить

Нужны Linux VPS, доступ по SSH, доменное имя и право менять его DNS. В этой конфигурации используются один контейнер приложения и Caddy. Практический стартовый ориентир — 2 vCPU, 2 ГБ RAM и 20 ГБ диска; это выбранный запас для контейнеров и копий, **не результат нагрузочного теста**. Локальные LLM на VPS не запускаются. Предел приложения в Compose — 1 ГБ RAM; `/tmp` до 256 МиБ входит в расход памяти контейнера и используется для временных медиа.

Установите Docker Engine и Compose plugin по инструкции для вашей ОС: [Ubuntu](https://docs.docker.com/engine/install/ubuntu/), [Debian](https://docs.docker.com/engine/install/debian/). Здесь не запускается удалённый скрипт установки и не удаляются существующие Docker-пакеты автоматически. Проверьте:

```bash
docker version
docker compose version
```

Далее команды выполняются в каталоге проекта. Если Docker требует права администратора, добавляйте `sudo` перед `docker`. На общем сервере доступ к Docker предоставляйте только доверенным администраторам: [официальные замечания Docker](https://docs.docker.com/engine/install/linux-postinstall/).

В DNS создайте A-запись, например `agents.example.com`, на IPv4 VPS. AAAA добавляйте только при рабочем IPv6. Для данной схемы сервер должен принимать TCP 80 и 443, а Caddy — иметь исходящий доступ к центру сертификации. Caddy получает и обновляет сертификат автоматически при корректных DNS и доступности портов: [требования Caddy](https://caddyserver.com/docs/automatic-https).

Настройте сетевые правила в панели провайдера: SSH разрешите с вашего административного адреса, TCP 80/443 — для доступа к сайту. Сначала проверьте SSH во втором окне; рабочую сессию не закрывайте до проверки. Эта инструкция не сбрасывает firewall. Опубликованные Docker-порты могут обходить обычные правила UFW; это прямо отмечено в [документации Docker](https://docs.docker.com/engine/install/ubuntu/#firewall-limitations). Порт приложения 8000 не публикуется.

## 2. Настройка и запуск

Распакуйте проект на VPS, перейдите в его каталог и выполните:

```bash
docker build --pull -t agentos:local .
docker run --rm -it --network none --user "$(id -u):$(id -g)" --mount "type=bind,src=$PWD,dst=/config" agentos:local python scripts/configure.py --domain agents.example.com --output /config/.env
docker compose config --quiet
docker compose up -d
docker compose ps
```

Замените домен своим. При необходимости добавьте к команде настройки `--username ваш_логин` (латиница, цифры, `_ . -`). Пароль задаётся дважды скрытым вводом, минимум 16 символов; в аргументы команды и историю shell он не попадает. `.env` создаётся с правами 0600, с новым Fernet-ключом и Argon2id-хешем. Существующий файл скрипт не перезаписывает.

В `.env` хеш хранится в **одинарных кавычках**: символы `$` должны оставаться буквальными. Не заменяйте их на двойные кавычки и не убирайте. Это соответствует [правилам интерполяции Docker Compose](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/#env-file-syntax). Не публикуйте вывод `docker compose config` без `--quiet`: он содержит подставленные секреты. Compose читает `.env` сам; выполнять `source .env` не нужно.

Откройте `https://ваш-домен`, войдите и включите TOTP 2FA. Сохраните TOTP-секрет вне сервера; отдельные recovery codes отсутствуют. Время VPS и телефона должно быть синхронизировано для TOTP. Добавьте API-провайдера и выполните небольшую первую задачу.

## 3. Сетевая и файловая схема

| Компонент | Доступ и данные |
| --- | --- |
| Caddy | Единственные публичные порты TCP 80/443; HTTPS и проксирование |
| Приложение | UID/GID 10001; один Uvicorn worker; только внутренняя сеть Compose |
| Файловая система приложения | Read-only; запись в named volume `/data` и ограниченный `/tmp` |
| `agentos_data` | SQLite, WAL, файл блокировки, локальные резервные копии |
| `caddy_data`, `caddy_config` | Состояние Caddy и TLS-сертификаты |
| `.env` на хосте | Хеш пароля и MASTER_KEY; не включён в Docker build context |

Имена реальных volumes получают префикс проекта `agentos_`. Не используйте `docker compose down -v`: этот флаг удаляет данные. Не масштабируйте `app`, не добавляйте Uvicorn workers и `--reload`: движок и polling должны иметь единственного владельца базы. Файловая блокировка останавливает второй процесс.

Uvicorn доверяет proxy-заголовкам в сети Compose; Caddy устанавливает адрес клиента. Не публикуйте `app:8000`, не присоединяйте к этой сети недоверенные контейнеры и не добавляйте внешние прокси без пересмотра списка доверенных proxy. Caddy admin API отключён; Docker socket не монтируется.

Пароли хешируются, ключи API и токены шифруются; **тексты задач и результаты в SQLite не зашифрованы целиком**. Администратор VPS/Docker, получивший `.env` и базу, сможет расшифровать токены. Защита приложения не заменяет защиту SSH и учётной записи VPS. Если ключ утрачен, восстановить зашифрованные токены и TOTP из одной базы нельзя.

## 4. Онлайн-копия базы

Обычное копирование работающего `.sqlite3` без WAL может дать неполную копию. Скрипт использует SQLite backup API и проверяет целостность готового файла; приложение можно оставить включённым.

```bash
docker compose exec -T app python scripts/backup.py
```

Скрипт напечатает путь вида `/data/backups/agentos-ДАТА.sqlite3` и его SHA-256. Скопируйте **именно показанный файл** на хост, заменив имя в следующей команде:

```bash
install -d -m 700 backups
docker compose cp app:/data/backups/agentos-ДАТА.sqlite3 backups/agentos-ДАТА.sqlite3
chmod 600 backups/agentos-ДАТА.sqlite3
```

Перенесите копию вне VPS по SSH/SFTP. Отдельно сохраните исходный `.env` в зашифрованном хранилище или менеджере секретов; не прикладывайте его к общедоступному архиву проекта. Копия базы содержит содержание задач. Копии, оставшиеся в `/data/backups`, занимают место: срок хранения выбирается владельцем, автоматического удаления нет.

Локально аналогичная команда:

```bash
.venv/bin/python scripts/backup.py --data-dir data
```

## 5. Восстановление с остановкой

Сначала обеспечьте наличие исходного `.env` с тем же `MASTER_KEY`. При переносе на другой сервер не запускайте повторную генерацию ключа. Скопируйте нужный файл в volume под именем `restore-input.sqlite3`:

```bash
docker compose cp backups/agentos-ДАТА.sqlite3 app:/data/restore-input.sqlite3
docker compose stop app
docker compose run --rm --no-deps --user 0 --cap-add CHOWN --cap-add DAC_OVERRIDE app chown 10001:10001 /data/restore-input.sqlite3
docker compose run --rm --no-deps app chmod 600 /data/restore-input.sqlite3
docker compose run --rm --no-deps app python scripts/restore.py /data/restore-input.sqlite3 --confirm-offline
docker compose up -d app
```

`--user 0` и две дополнительные capabilities нужны только для владельца импортированного файла; рабочий сервис остаётся UID 10001 без capabilities. На новом сервере сначала создайте контейнер и volume через `docker compose create app`, затем `docker compose cp`. Права скопированного файла можно исправить без запуска сервера:

```bash
docker compose run --rm --no-deps --user 0 --cap-add CHOWN --cap-add DAC_OVERRIDE app chown 10001:10001 /data/restore-input.sqlite3
docker compose run --rm --no-deps app chmod 600 /data/restore-input.sqlite3
```

После этого выполните команду `restore.py` и `docker compose up -d`. Исходный файл копии не меняется. Перед заменой существующая база сохраняется в `/data/backups/before-restore-....sqlite3`. Скрипт проверяет целостность, версию схемы, зашифрованные поля и соответствие ключа. Флаг `--confirm-offline` подтверждает замену; дополнительно файловая блокировка запрещает восстановление при работающем приложении.

После восстановления веб-сессии сброшены, выполнявшиеся задачи стоят на паузе, незавершённое планирование возвращено в backlog. Подтверждённые, ещё не отправленные публикации снова становятся черновиками; незавершённая отправка получает `uncertain`. Telegram отключён и старый offset очищен: проверьте состояние, затем включите интеграцию вручную. Опубликованные после даты резервной копии материалы могли сохраниться в соцсети — сравните их перед новым подтверждением и отправкой.

Локальное восстановление после остановки `run-local.py`:

```bash
.venv/bin/python scripts/restore.py data/backups/agentos-ДАТА.sqlite3 --data-dir data --env .env --confirm-offline
```

## 6. Обновление

Сделайте копию базы и сохраните текущую версию исходников/образа. Замените код проекта, сохранив `.env`. Обновите образ приложения и Caddy, затем перезапустите:

```bash
docker compose build --pull app
docker compose pull caddy
docker compose up -d
docker compose ps
```

Проверьте вход, состояние задач и небольшую пробную задачу. Откат к прежнему коду допускается только с совместимой схемой базы; для будущих несовместимых изменений потребуется восстановление подходящей копии. В текущей версии схема имеет `user_version=1`. Образы `python:3.12-slim-bookworm` и `caddy:2-alpine` обновляемые, не закреплены по digest; перед рабочим обновлением проверьте новую сборку отдельно.

## 7. Смена пароля и восстановление доступа

С доверенной SSH-консоли остановите приложение и запустите помощник. Он проверяет файловую блокировку, запрашивает новый пароль скрыто, сохраняет прежний `MASTER_KEY` и сбрасывает веб-сессии. Права и владелец `.env` сохраняются; дополнительные копии секретов не создаются.

```bash
docker compose stop app
docker compose run --rm --no-deps --user 0 --cap-add CHOWN --cap-add DAC_OVERRIDE --volume "$PWD:/setup" app python scripts/reset-admin.py --env-file /setup/.env
docker compose up -d app
```

2FA по умолчанию остаётся включённой. Если телефон и сохранённый TOTP-секрет потеряны, **добавьте `--reset-2fa`** к команде помощника; после входа настройте 2FA заново. Этот путь доступен администратору сервера, а не посетителю сайта. Временное повышение прав относится только к отдельному офлайн-контейнеру восстановления; обычный `app` остаётся без capabilities. Не меняйте `.env` целиком новым файлом: новый MASTER_KEY несовместим со старой базой.

Локально после остановки сервера:

```bash
.venv/bin/python scripts/reset-admin.py --env-file .env --data-dir data
```

## 8. Диагностика

```bash
docker compose ps
docker compose logs --tail 100 app
docker compose logs --tail 100 caddy
```

| Симптом | Что проверить |
| --- | --- |
| Ошибка выпуска TLS | A/AAAA, доступность 80/443, занятость портов другим веб-сервером |
| `app` unhealthy | Домен и PUBLIC_URL, мастер-ключ, права volume, отсутствие второго процесса |
| Не проходит вход / Host / Origin | Используйте ровно PUBLIC_URL; для HTTP есть только отдельный localhost-режим |
| API не отвечает | Ключ, точное имя доступной модели, баланс, ограничения аккаунта и исходящий доступ с VPS |
| Telegram молчит | Бот включён, токен верен, ваш числовой user ID в allowlist, сообщение отправлено в личный чат |
| Публикация `uncertain` | Проверьте соцсеть вручную: сетевой обрыв мог случиться после приёма публикации |

Внешние API, авторизации ваших соцсетей, реальный VPS и автоматическое получение HTTPS-сертификата не были доступны для боевой проверки при сборке проекта. Docker-конфигурация подготовлена для запуска; работоспособность именно вашего окружения подтверждается приведёнными проверками после развёртывания.
